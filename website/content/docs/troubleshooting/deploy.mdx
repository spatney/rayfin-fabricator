title: "Publishing and Fabric problems"
description: "Fix failed publishes, publishing after each chat turn, Fabric authentication, semantic model reads, Rayfin CLI errors, and sharing access."
---

Use this page when Fabricator can't publish your app to Microsoft Fabric, or the published app isn't the version you expect. Fabricator used to call publishing "deploying", and a few headings on this page keep that word.

## A deploy failed

You see a "Couldn’t publish" message, the publish control in the app bar says "Failed" next to the published app's name and offers **Try again**, and Ray swims in above the preview to say "Your app didn’t make it to Fabric. Want me to find out why?" If you've sent Ray away, the notice says "Couldn’t publish this app. Help can find out why." A build failure's log can say "❌ Deployment failed: Static build command failed. Fix the build errors and re-run, or use 'rayfin up staticapp deploy --skip-build' to deploy existing content."

![Ray above the preview after a failed publish, saying "Your app didn't make it to Fabric. Want me to find out why?", with Find out why and View logs beside him.](/screenshots/deploy-error.webp)

Fabricator publishes with the project's pinned Rayfin CLI, running `rayfin up -y --force`. The log is the source of truth: it includes Rayfin CLI output, dependency recovery, build errors, Fabric authentication failures, workspace targeting errors, and Fabric API failures.

1. Select **Find out why**, or select Ray. Help opens and asks "Why did my last publish fail?" for you. It reads the end of the publish log, explains the cause in plain language, and offers the fix as a button when there is one.
2. To read the log yourself, select **View logs**. Read the first real error near the end. Ignore a final generic "Deployment failed" line if a more specific line appears above it. The `Details:` line under the error usually says why, such as "Details: The PostgreSQLDatabase feature is not enabled."
3. If the log says "This project has no Fabric workspace yet — choose one to publish to.", select **Publish** in the app bar and pick a workspace.
4. If the log mentions authentication, expired credentials, a token-cache lock, `HTTP 401`, or `unauthorized`, use **Refresh Fabric authentication**, then select **Try again** in the app bar.
5. If the log mentions a build or TypeScript error, send the prompt below in chat, then publish again.
6. If the log says "Environment variable '…' referenced in rayfin.yml (…) is not defined.", your app's `rayfin/rayfin.yml` uses a setting that isn't set on this computer. Add that variable to the project's `rayfin/.env`, then select **Try again**.
7. If the log says "Failed to create Rayfin item" with "Details: The feature is not available", Fabric apps aren't available in that workspace. See [Fabric apps aren't available in the workspace](/docs/troubleshooting/deploy#fabric-apps-arent-available-in-the-workspace).
8. If the log mentions Fabric capacity, permissions, a workspace conflict, or a Fabric API failure, fix that Fabric workspace issue and select **Try again**.
9. If the log mentions destructive data-model changes, note that Fabricator already publishes with `--force`; the failure is coming from the CLI or Fabric after that forced attempt.

```prompt title="Fix the build errors"
Publishing my app failed because it doesn't build. Find and fix the build and TypeScript errors, and check that the app builds without errors.
```

To put the notice away, select the **×** beside it. It comes back if the next publish fails.

If the log is unclear, [Report a problem](/docs/troubleshooting/report-a-problem) and attach diagnostics.

## The preview says Choose where to publish

The preview says "Choose where to publish" and "`<name>` hasn’t been published yet. Select Publish in the header above to name it and pick the Fabric workspace to publish it to."

A publish found no Fabric workspace for the app, and the publish log says "This project has no Fabric workspace yet — choose one to publish to." Fabricator asks where to publish it instead of choosing a workspace for you.

1. In the app bar, select **Publish**.
2. Optionally enter a **Name** for the published app.
3. Under **Publish to workspace**, pick a workspace, and select **Publish**.

If publishing fails, see [A deploy failed](/docs/troubleshooting/deploy#a-deploy-failed).

## Automatic redeploy stopped

After a successful chat turn, your app isn't published any more, and you have to publish it from the app bar.

Fabricator publishes after a turn only while **Publish after each chat turn** is on. It's off until you turn it on in the publish control's panel, and it publishes only an app you've already published yourself. If an earlier version of Fabricator published your apps after each turn without you turning this on, it's off now. When it's on, Fabricator publishes after a successful turn when it can confirm there are changes since the last published version. If the last published version is unknown, the next successful turn publishes once to establish it. If the check for changes fails, you see "Couldn’t publish automatically", with a message that ends "Select Publish to publish your changes."

1. In the app bar, select the publish control, and check **Publish after each chat turn** in its panel. Turn it on if you want each turn to publish.
2. Confirm the chat turn finished successfully. Failed, stopped, or cancelled turns don't publish.
3. If you see "Couldn’t publish automatically", select **Publish** in the app bar.
4. If you switched to another published app, publish once from the app bar, where the button says **Publish changes** or **Publish**, to record its published version.
5. If a publish is already running, wait for it to finish before sending another turn.
6. If publishing from the app bar works but publishing after each turn keeps stopping, keep publishing from the app bar as a workaround and [Report a problem](/docs/troubleshooting/report-a-problem).

This is an open reliability issue for some long sessions.

## Fabric authentication blocks publishing

A publish repeatedly fails even though setup shows you signed in, or the notice above the preview says "Fabric wants you to sign in again before you can publish this app." and offers **Refresh Fabric authentication**.

![The account menu opened from the avatar in the top-right corner, showing the signed-in Fabric account with Manage accounts, Refresh Fabric authentication, Sign out and Settings.](/screenshots/account-menu.webp)

Fabricator publishes with the Rayfin CLI credentials for the project. **Refresh Fabric authentication** runs the selected project's `rayfin logout`, then `rayfin login`, and verifies the refreshed credential against Fabric. It does not clear Copilot, Azure CLI, or preview-browser sessions.

1. Select **Refresh Fabric authentication** in the notice above the preview, or open the account menu in the app bar and select it there.
2. In the dialog, select **Clear credentials and sign in**.
3. Complete the browser sign-in.
4. Wait for Fabricator to say "Fabric authentication is verified. Publish again to retry."
5. Select **Try again** in the app bar. Refreshing authentication doesn't publish by itself.

If refresh fails, update the app's Rayfin packages to Rayfin 1.35.1 or newer from the Rayfin version control, then try again. If it still fails, [Report a problem](/docs/troubleshooting/report-a-problem).

## Couldn't read the semantic model

In Blueprint, a semantic model shows "Couldn’t read the semantic model", sometimes with "The API returned a URL outside the authenticated service."

Fabricator reads semantic model metadata live from Fabric and Power BI APIs. The URL validation error was fixed after earlier releases by allowing Fabric, Power BI, and regional `analysis.windows.net` continuation hosts while still rejecting unrelated URLs.

1. Update to the latest Fabricator version.
2. Use **Refresh Fabric authentication** for the project.
3. If the view offers **Sign in to Fabric**, **Sign in to Azure** or **Sign in & retry**, select it and complete sign-in.
4. Confirm you have access to the workspace and edit or write access when the semantic model definition requires it.
5. Select **Try again** in the semantic model view.

If the same exact message appears on the latest version, [Report a problem](/docs/troubleshooting/report-a-problem).

## The workspace or capacity blocks publishing

The workspace list or the publish log says a workspace has no eligible Fabric capacity, the capacity is unavailable, or you do not have permission.

Rayfin apps are published to a Fabric workspace backed by an eligible Fabric capacity. Fabricator can list workspaces and capacity metadata, but publishing still depends on your tenant permissions and Fabric capacity state.

1. Choose a workspace backed by an active Fabric capacity.
2. If the capacity is paused or unavailable, resume it in Fabric or choose another workspace.
3. Confirm your account can publish to the workspace.
4. If you are in a client tenant, make sure you completed Fabric sign-in for that tenant.
5. Select **Try again** in the app bar.

If you cannot see the right workspace or capacity, contact your Fabric administrator or [Report a problem](/docs/troubleshooting/report-a-problem) with the publish log.

## Fabric apps aren't available in the workspace

Publishing stops and Ray says "That workspace’s capacity is in UK South, and Fabric apps aren’t there yet. Let’s pick a workspace in another region.", naming your workspace's region. If you've sent Ray away, the notice says "This workspace’s capacity is in UK South, where Fabric apps aren’t available yet. Choose a workspace in another region." The publish log says "✖ Failed to create Rayfin item: Fabric API error: 403 Forbidden" with "Details: The feature is not available", and then "Couldn't publish: Fabric apps aren’t available in “Sales”, a workspace on a capacity in UK South.", with your workspace's name and region.

Fabric apps aren't available in every Fabric region yet, and a workspace is in the region of the Fabric capacity it's on. Fabricator doesn't keep a list of regions, because which regions have Fabric apps changes: it goes by what Fabric answers when you publish. Fabric created nothing in that workspace, so your app stays published where it was, if it was published before.

1. Above the preview, select **Choose another workspace**. The publish control's panel in the app bar offers **Choose another workspace** too.
2. Pick a workspace that isn't marked "Fabric apps unavailable". For the rest of the session, the workspace picker marks the workspace Fabric turned down, and the other workspaces on its capacity or in its region, and lists them last. Publishing to a marked workspace asks you first: select **Publish here anyway** to try it.
3. If none of your workspaces is in another region, select **+ New workspace** and choose a capacity in another region. Capacities in a region Fabric turned down are listed last.
4. Select **Publish**.

To see which regions have Fabric apps, select **Region availability**. It opens Microsoft's [Fabric region availability](https://learn.microsoft.com/fabric/admin/region-availability) page, where regions without them list "Fabric App (preview)" as not available.

The same message can mean that Fabric Apps isn't turned on for your organization. If Fabric turns down workspaces in more than one region, ask your Fabric administrator to turn on **Fabric Apps (preview)** in the tenant settings of the Fabric admin portal. If it still fails, [Report a problem](/docs/troubleshooting/report-a-problem).

## Rayfin CLI or npm package resolution failed

The publish log says the Rayfin CLI could not be found, npm reports `ETARGET`, or project dependency installation fails before `rayfin up` starts.

Current Fabricator versions use the Rayfin CLI pinned in each project, and refresh npm's package information when they create a project. Older releases had global Rayfin CLI checks and a stale npm metadata problem that could produce `ETARGET` even when the package existed.

1. Update to the latest Fabricator version.
2. Open the project and let dependency installation finish.
3. Select **Try again** in the app bar.
4. If npm still reports missing or unresolved packages, repair project dependencies with `npm ci` when `package-lock.json` exists, or `npm install` otherwise.
5. Do not install a global Rayfin CLI as the primary fix; Fabricator publishes through the project-pinned CLI.

If package resolution keeps failing, [Report a problem](/docs/troubleshooting/report-a-problem) and include the npm error.

## A new app's packages won't install

You create or open a new app and see **Couldn't install project dependencies**, or Fabric sign-in or a publish fails, with "npm install failed (exit code 1): Cannot read properties of null (reading 'edgesOut')".

This is a bug in npm 10, the npm that comes with Node.js 22. Since vitest 4.1.12 was published, npm 10 stops with this error when it installs a new app's packages. Apps whose packages are already installed aren't affected.

Fabricator 1.27.1 and later work around it: when npm can't work out an app's packages like this, Fabricator installs them again with npm's `--legacy-peer-deps` option. The output says "npm couldn't work out the packages' peer dependencies; retrying with --legacy-peer-deps...".

1. Update to the latest Fabricator version.
2. Open the app. If it shows **Couldn't install project dependencies**, select **Retry installation**.
3. If it still fails, install the current LTS release of Node.js from [nodejs.org](https://nodejs.org). It comes with npm 11, which doesn't have this bug. Then restart Fabricator, open the app and select **Retry installation**.

If it keeps failing, [Report a problem](/docs/troubleshooting/report-a-problem) and include npm's error and the log it names.

## Recipients can't open the shared app

You shared a published app, but another person cannot open it.

Publishing and sharing are separate. Fabricator's share flow grants app access in the target tenant, and for semantic models in other workspaces it grants Build access to those models.

1. Confirm the app is published and live.
2. Use the share flow again for the recipient's work email.
3. Confirm the recipient belongs to the same Microsoft Entra tenant or has the required guest access.
4. For semantic-model apps, confirm they also have access to the model's workspace or Build permission on the model.
5. See [Share your app](/docs/ship/share) for the normal flow.

If sharing still fails, [Report a problem](/docs/troubleshooting/report-a-problem).
