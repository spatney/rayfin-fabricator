---
title: "Keep Rayfin up to date"
description: "Know when a project's Rayfin CLI and SDK are out of date, and let Copilot upgrade them together while keeping the app building."
---

Each Rayfin app pins its own Rayfin CLI and SDK packages. Fabricator reads those installed package versions and offers updates in the status bar: to Rayfin's latest release that it runs on this computer, so your app keeps running here, and to newer releases, such as previews, with a warning that they might be unstable.

![The Rayfin version control in the status bar, opened to show that the Rayfin CLI and SDK can be updated from 1.35.1 to 1.36.2 with Update with Copilot.](/screenshots/rayfin-version.webp)

## Read the Rayfin status

When an update is out, the status bar shows the project's version as `Rayfin v<version>`, followed by the version it updates to, such as `↑ 1.36.2`: Rayfin's latest release that Fabricator runs on this computer. When the only newer release isn't Rayfin's latest yet, such as a preview, the status bar shows `Rayfin v<version>` alone. When the project is on the newest release, the status bar shows nothing for Rayfin.

Open it to see separate rows for:

- **Rayfin CLI**
- **Rayfin SDK**

The version checker reads `@microsoft/rayfin-cli` as the CLI package. Other `@microsoft/rayfin-*` packages are treated as SDK packages.

## Update with Copilot

When an update is available:

1. Select the Rayfin version in the status bar.
2. Review the version rows.
3. Select **Update with Copilot**.

On **Your projects**, a project with an update shows its version followed by **Update**, such as `Rayfin 1.35.1 · Update`. Select **Update** to open the project and send the same request, without opening the status bar.

Fabricator sends a prepared upgrade request to the Build chat. Copilot is asked to:

- set exact Rayfin package versions in `package.json`,
- run `npm install`,
- keep Rayfin SDK packages in lockstep,
- pin Rayfin connector packages to the new CLI version when the app uses them,
- check the installed Rayfin docs for deprecations and known limitations,
- update app code so it still builds and runs,
- not run `rayfin up` or publish the app itself.

The update reaches your published app the way any chat change does: when the turn finishes, if **Publish after each chat turn** is on and the app is published, and otherwise the next time you publish. The popover says which: "They reach Fabric when Fabricator publishes the app after the turn." or "They reach Fabric the next time you publish." A team app's update reaches Fabric when you publish it, through the team pipeline.

## Update to a newer release, such as a preview

Rayfin publishes some releases before they become its latest release (the one npm's `latest` tag names), such as Rayfin 2.0.0 while its latest release is 1.36.2. Fabricator doesn't stop you from using them, but they might be unstable. New projects stay on the release line Fabricator starts them on, such as 1.36.x, so you choose when an app moves.

1. Select the Rayfin version in the status bar.
2. Under "Rayfin `<version>` is available", read why the release needs care. A release that isn't Rayfin's latest says "It isn’t Rayfin’s latest release yet, so it might be unstable." A release the local backend doesn't run yet says "Fabricator doesn’t run it on this computer yet, so some things might not work as expected here."
3. Select **Update to `<version>` with Copilot**.

Copilot gets the same request as with **Update with Copilot**, for that release, and is told why it needs care, so its summary reminds you. A newer release can change APIs your app uses, so Copilot also updates the app's code for what changed.

You can also ask for a release in the chat:

```prompt title="Move to a newer Rayfin release"
Upgrade this app to Rayfin 2.0.0. Move every Rayfin package, the CLI included, to that exact version, run npm install, then check the installed Rayfin docs for what changed and update the app so it still builds and runs.
```

## Releases Fabricator runs on this computer

Fabricator runs your app on this computer with a local backend that runs some lines of Rayfin releases, such as 1.36.x and 2.0.x. So:

- **Update with Copilot** offers Rayfin's latest release that the local backend runs.
- New projects, team apps included, start on one of those lines, such as 1.36.x, and pin every `@microsoft/rayfin-*` package to it with a `~` range, such as `~1.36.0`, so a later `npm install` doesn't move them to another release.
- The Advisor flags **Rayfin packages aren't pinned to a release Fabricator runs locally** when a package is on a release older than those lines, or declared with a range that lets the next install leave its line.

An app on a newer release than the local backend runs still runs on this computer, but a note above the preview says some things might not work as expected. See [The preview says some things might not work](/docs/troubleshooting/preview#the-preview-says-some-things-might-not-work). An app on an older release can misbehave on this computer. Once it's published, its preview uses the published app's backend instead. See [What runs only on Fabric](/docs/build/local-development#what-runs-only-on-fabric).

## Why lockstep matters

Rayfin packages ship as a family. The Advisor rule catalog checks that the SDK packages are on one version because mixing `@microsoft/rayfin-core`, `-client`, `-data`, `-auth`, `-auth-provider-fabric`, `-lib`, `-functions`, `-storage`, `-embed-host`, and `-local-dev` versions is untested and can break at runtime.

The CLI and SDK version independently, but newer releases carry fixes and match the current docs. See the [Rayfin changelog](https://rayfin.ai/docs/reference/changelog).

## Minimum version for current Fabricator features

Team workspaces require Rayfin **1.36.2 or newer**. New projects, team apps included, start on the newest release of the line Fabricator starts new projects on, pinned to that line.

Older existing projects keep their pinned dependencies until you update them.

If you move an app into a team workspace, update older apps first with **Update with Copilot**.

## If dependencies are missing

When you open a project, Fabricator checks that the project's Rayfin CLI and the rest of its packages are fully installed, and installs any that are missing or incomplete before enabling the project tools. The check usually takes a moment. If it takes longer, you see a `Preparing <project name>` status and "Checking the project's Rayfin CLI and installing missing dependencies..." It checks again before it publishes or signs in to Fabric.

If installation fails, Fabricator shows **Couldn't install project dependencies** with npm's error, **Retry installation** and **Switch projects**. When npm can't work out the packages' peer dependencies, Fabricator installs them again with npm's `--legacy-peer-deps` option first. See [A new app's packages won't install](/docs/troubleshooting/deploy#a-new-apps-packages-wont-install).

When your app's packages, or its functions' packages, aren't installed, the preview says "Your app’s packages aren’t installed" and offers **Install dependencies**. See [When your app doesn't start](/docs/build/preview#when-your-app-doesnt-start).

## Manual upgrade prompt

Use this if you want to start the upgrade yourself from the chat instead of the status-bar button. Like **Update with Copilot**, it moves the app to Rayfin's latest release, not to a newer preview:

```prompt title="Upgrade Rayfin packages"
Upgrade this app to Rayfin's latest release, the one npm's latest tag names. Keep all Rayfin SDK packages on the same exact version, update the Rayfin CLI package too, run npm install, then check the installed Rayfin docs for deprecations or known limitations and update the app so it still builds.
```
